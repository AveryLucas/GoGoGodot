# POC #4 — Lifecycle Ordering

**Status:** PASS (with two newly-discovered hooks worth documenting)
**Date:** 2026-05-21
**Graphics.GD version:** `v0.0.0-20260521203745-bcb92de10087`
**Godot version:** `4.6.2.stable.official.71f334935`

## Hypothesis

ARCHITECTURE.md §9 and DESIGN_PRINCIPLES rule 9 say:

> Defaults go in constructors (`NewX`), not in `Ready`. Editor-set values override constructor values; `Ready`-set values trample them.

Implied ordering: **constructor → property deserialize (.tscn inspector overrides) → child wiring → `Ready`**.

## Test setup

A `Probe` with:
- `HP int` field (zero-value 0).
- `Helper Node.Instance` exported child.
- `NewProbe()` constructor (registered via `classdb.Register[Probe](NewProbe)`) sets `HP = 100`.
- Optional hooks `Init()` and `OnCreate()` (found by reading `register_class.go:782-796`).
- `main.tscn` overrides `hp = 42` and includes a pre-authored `Helper` child.

Each callback logs a sequence number so we can read the order directly.

## Result

✅ **Order confirmed.**

```
[POC4] 01  main                registering Probe with NewProbe constructor
[POC4] 02  main                calling startup.Scene()
[POC4] 03  NewProbe            setting HP=100 (constructor default)
[POC4] 04  OnCreate            observed HP=100
[POC4] 05  Init                observed HP=100
[POC4] 06  Ready               observed HP=42  Helper.populated=true
[POC4] 07  Process             HP=42 — exiting
```

Resolved order: **`NewProbe` → `OnCreate` → `Init` → (.tscn property deserialize) → (child wiring) → `Ready` → `Process`**.

## Findings

### 1. ✅ "Defaults in constructors" rule is validated

`NewProbe` sets `HP=100`. By the time `Ready` runs, the inspector value `hp=42` has overwritten it. This is exactly the behaviour DP rule 9 promises — and conversely, anything you set in `Ready` would clobber the inspector value, which is why the doc forbids it.

### 2. ⚠️ Two undocumented hooks: `OnCreate` and `Init`

Graphics.GD calls **both** `OnCreate()` and `Init()` after the constructor and before property deserialize. They see the constructor's `HP=100`. Neither is mentioned in ARCHITECTURE.md.

| Hook | Fires | Sees |
|---|---|---|
| `NewProbe` (constructor) | first | zero-value fields |
| `OnCreate()` | second | constructor-set values |
| `Init()` | third | constructor-set values |
| (deserialize) | fourth | — overwrites inspector-set fields |
| (child wiring) | fifth | — populates Node fields |
| `Ready()` | sixth | post-deserialize, post-wiring state |

There's also an `OnCreate(value reflect.Value)` two-argument form in `register_class.go:787-790` not tested here. Skipping for now — the zero-arg form is the user-facing surface.

**Action items for gogogd:**
- Document `OnCreate` and `Init` exist. Either expose them through wrapper types or explicitly reserve them as "do not use; gogogd may need these later."
- **Recommendation:** reserve them. Three lifecycle entry points (`NewX`, `Ready`, `Process`) is the simple story. Adding `OnCreate`/`Init` to the user surface bloats the mental model without giving them anything `NewX` doesn't.
- Phase 1 wrapper-type `*Ext[T]` shims should define `OnCreate` / `Init` as private use (e.g. internal `gogogd` setup like strict-mode wiring) and panic if a user-defined struct overrides them.

### 3. ✅ Inspector property names use snake_case

The `.tscn` line `hp = 42` (lowercase) successfully overrode the Go field `HP`. Same convention as POC #3 method names. Confirms verified fact #3 (exported fields auto-snake_case'd).

### 4. ✅ Constructor registered via variadic arg works

Pattern from `register_class.go:297`:

```go
classdb.Register[Probe](NewProbe)
```

…where `NewProbe` is a `func() *Probe`. The runtime detects the `New`-prefix + zero-arg + `*T`-return signature and installs it as the engine-side constructor. **This must be wired up by `gogogd register` codegen** for any class whose package declares a `NewT` matching the signature. Without it, the engine calls a default `&Probe{}` constructor and `NewProbe` is dead code.

### 5. Order-of-callbacks correctness has implications for the wrapper types

Phase 1 hand-written wrapper types (`NodeExt[T]`, `Node2DExt[T]`, …) may want to do bookkeeping at *some* lifecycle phase. The right phase depends on what:

| What | Right phase | Why |
|---|---|---|
| Default values | `NewT` | Will be overridden by .tscn, which is correct |
| Helper allocations independent of node tree | `OnCreate` (or `NewT`) | Before deserialize, no scene-dependent state available yet |
| Cache `As*` references / pin handles | `Init` (or `Ready`) | After construction, safe to call `AsNode()` |
| Validate child structure (`ggd:"strict"`) | `Ready` | After child wiring, all fields populated |
| Subscribe to signals on children | `Ready` | Children must exist first |
| Start work that depends on the tree | `Ready` | First moment the tree state is canonical |

Phase 1's wrapper-type `Ready` shim — which auto-runs `gogogd.AssertStrict(self)` (POC #2's outcome) — sits at the right place.

## What this means for the plan

| Plan item | Action |
|---|---|
| DESIGN_PRINCIPLES rule 9 | Keep as written, fully validated |
| ARCHITECTURE.md §9 | Add `OnCreate` and `Init` to the lifecycle table. Note they're available but reserved for gogogd internals (decision pending) |
| `gogogd register` codegen | Detect `func NewT() *T` in the same package and pass it to `classdb.Register[T](NewT)`. Without this, the constructor is never used |
| Phase 1 wrapper types | `*Ext[T].Ready()` is the right place for strict-mode wiring (POC #2). `OnCreate`/`Init` are not user-facing |
| Educational docs | Show the order explicitly in §14's tutorial ramp. "Set defaults in NewX, set scene-driven state in Ready" is the rule users need to internalize |
