# POC #7 — Signal Owner-Bound Auto-Disconnect on `ExitTree`

**Status:** PASS — confirms the divergence DESIGN_PRINCIPLES rule 2 exists to fix
**Date:** 2026-05-21
**Graphics.GD version:** `v0.0.0-20260521203745-bcb92de10087`
**Godot version:** `4.6.2.stable.official.71f334935`

## Question

DESIGN_PRINCIPLES rule 2 says `signal.Connect(owner, fn)` should auto-disconnect when `owner.ExitTree()` fires. Does Godot provide this for free (and gogogd just re-exports it), or does gogogd need to implement it?

## Test

Three sibling nodes connect to an Emitter's `Tick` signal in distinct ways:

| Listener | How it connects | Bound to what |
|---|---|---|
| `GoListener` (Go) | `signal.Attach(Callable.New(func(n int){...}))` via `Object.Signal("tick")` | **nothing** — bare Go func |
| `GdListener` (GDScript) | `emitter.tick.connect(self._on_tick)` | `self` — the GDScript node |

Both `queue_free` themselves at scene-frame 3. The Emitter keeps emitting through frame 6 and we observe both whose handlers fire and `HasConnections()`.

## Findings

### 1. ✅ GDScript-side connections auto-disconnect for free

`emitter.tick.connect(self._on_tick)` produces a callable bound to `self`. When `self.queue_free()` runs, Godot's internal signal bookkeeping sees the bound object die and stops dispatching to it. `[POC7][GD]` lines disappear cleanly at frame 4.

This is the "auto-disconnect for free" path — gogogd doesn't need to re-implement it for GDScript-style usage.

### 2. ⚠️ Go-side `Callable.New(fn)` is unbound — connections DO NOT auto-disconnect

`Callable.New(func(n int) { ... })` wraps a bare Go function with no Object binding. Godot has nothing to track, so the connection stays live forever — even after the Probe that "owns" the closure is freed. POC #7 shows the handler firing happily on frames 4–6 with the listener gone.

**Combined with POC #6** (closures don't pin handles), this is a real two-sided footgun:
- Connection never tears down → leak grows over time.
- Closure's captured handles invalidate in 2 frames → handler eventually fires with dead refs → crash or silent corruption.

The only thing saving POC #7's GoListener from crashing was that its closure captured nothing dangerous (`os.Stderr` is a Go global).

### 3. ✅ The leak is exactly what `gogogd.Connect(owner, fn)` exists to solve

DESIGN_PRINCIPLES rule 2:

> Signal connections take an owner via `Connect(owner, fn)`. Raw upstream `signal.Call(fn)` is available but discouraged — connections without owners leak.

POC #7 is the *empirical proof*. The mechanism Phase 1 ships:

```go
// Phase 1 sketch.
func Connect[S any](owner Node.Instance, sig *S, fn any) Handle {
    cb := Callable.New(fn)
    sig.Attach(cb)                              // upstream connect

    // Watch owner's tree_exited signal. When fired, remove the connection.
    owner.AsObject().Signal("tree_exited").Attach(Callable.New(func() {
        sig.Remove(cb)
    }))
    return Handle{cb: cb, sig: sig}
}
```

The cleanup is itself a signal connection on `owner` — but `tree_exited` is bound to a self-managing engine signal that goes away with the node, so it doesn't recurse.

(There's a subtle "what owns the cleanup callable" question — the cleanup callable IS unbound too. But it executes exactly once when `owner` exits the tree, after which it's removed by Godot's own signal flush. Phase 1 implementation will need to verify this with a small spike.)

### 4. ⚠️ `HasConnections()` lies — slot stays even after the bound object is freed

Even though `GdListener` was freed at frame 3 and its handler stopped firing, `Emitter.Tick.HasConnections()` still returned `true` on frames 4–6. Godot lazily prunes the connection list; introspection during the interim sees the dead slot.

**Action:** gogogd's `signal.HasConnections()` (if exposed) should warn in its docstring that this is approximate. Or — better — gogogd's `Connect` helper maintains its own owner-keyed connection table for accurate counting, in addition to forwarding to upstream's signal.

### 5. ✅ Symmetric finding for any owner-less helper

The same diagnosis applies to **`After(dt, fn)`**, **`Every(dt, fn)`**, **`Bus.On("x").Call(fn)`** — any helper that wraps a `func` without an owner takes the same leak path. DESIGN_PRINCIPLES rule 1 (helpers take an owner first arg) is necessary, not stylistic.

## What this means for the plan

| Plan item | Action |
|---|---|
| Phase 1 `gogogd.Connect(owner, sig, fn)` | **Required.** Attaches the callable, registers `owner.tree_exited` cleanup. Sketch above |
| `gogogd.Signal.Call(fn)` re-export | Keep available as the unsafe-but-quick path. Document the leak. The verbose-but-safe path (`Connect(owner, ...)`) is the recommendation |
| Convenience shortcuts (`node.OnPressed(fn)`, etc.) | These wrap `Connect` with `node` as the implicit owner. Auto-cleanup falls out for free |
| `gogogd doctor` lint | Flag any direct use of `signal.Call(fn)` / `signal.Attach(...)` outside `gogogd` package as "did you mean `gogogd.Connect`?" |
| Phase 0 follow-up | Verify the "cleanup callable on `tree_exited` doesn't leak" claim with a small spike during Phase 1A implementation |
| Docs | Lifetime/cleanup page: side-by-side example showing the leak (`signal.Call(fn)` after free) vs. the fix (`gogogd.Connect(owner, sig, fn)` after free) |
