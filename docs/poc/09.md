**Date:** 2026-05-21
**Graphics.GD version:** `v0.0.0-20260521203745-bcb92de10087`

## The §1.6 claim

ARCHITECTURE.md §1.6 reload budget:

> The 2-second target decomposes as ~600ms Go compile + ~300ms link + ~50ms IPC + ~1s scene reload. If any component blows its budget, that's a design-defending forcing function — for example, if `gd build` consistently takes >1.5s, we either accept a slower target or look for incremental-build improvements upstream.

## Where the 5.7s goes

A `go build -x` trace shows essentially **one** action: the link step. The Go compiler cache absorbs every package; user-code recompilation is invisible. The link command:

```
link.exe -o windows_amd64.dll -importcfg ... -buildmode=c-shared
  -extld="C:\Users\hello\gd\bin\zig.exe cc"
  <hundreds of cached package files>
```

Graphics.GD's package layout — every Godot class in its own package — means the link step pulls in **hundreds of small archive files**. The `-buildmode=c-shared` mode forces zig cc to run as the external linker, producing a 19MB DLL. That linking + producing the c-shared artifact is the entire cost.

## Findings

### 1. ❌ The 2-second `save → playable` promise can't be made today

On a fast Windows 11 machine with Go 1.26.2 — likely a representative target user setup — the round-trip is ~6 seconds. Calling this "under 2s" in marketing/docs would be false advertising.

### 2. ✅ Asset and scene tiers ARE within budget

§1.6's three-tier reload model:

| Tier | §1.6 target | Reality |
|---|---|---|
| Asset (`.png`/`.ogg`/`.tres` change) | <500ms | Plausible — handled by Godot import pipeline, doesn't touch Go |
| Scene (`.tscn` change) | <1s | Plausible — same; Godot reloads its own files |
| Code (`.go` change) | <2s | **~6s actual** |

Tiers 1 and 2 should be the "60% case during polish phase" that §1.6 calls out. They actually deliver the "instantaneous" feel the doc promises. **The code-tier promise is the only one to revise.**

### 3. ⚠️ Project size barely matters

POC #1 (60 lines, 4 imports) and POC #8 (wrapper-type layer, more code, more imports) both build in 5.7s. The bottleneck is the link step, which is dominated by Graphics.GD's package count, not user code. **This is good news for scaling**: a real production game with 50+ components likely builds in the same ~6s, not worse.

### 4. ⚠️ Cold builds are 100+ seconds

First checkout (empty `GOCACHE`) takes 104s on this machine. That's not a dev-loop concern (it happens once) but it's a serious first-impression concern: `gogogd new my-jam && cd my-jam && gogogd dev` will sit on the user for nearly two minutes the first time. The "5-minute fresh-start to playable" Phase 1 exit criterion in IMPLEMENTATION_PLAN.md is tight if 100s of that is Go compile.

### 5. The c-shared mode adds ~2.4s on top of regular linking

Regular `go build` (no c-shared): 3.1s. With c-shared: 5.7s. The 2.4s delta is zig cc's work to produce a Windows DLL with proper exports. This is mostly inherent to the cgo + c-shared model — not a Go limitation that will go away.

## Options for the plan

In order of preference:

### Option A (recommended): Revise the budget honestly

Restate the §1.6 target as:
- **Asset reload: <500ms** ✅ unchanged
- **Scene reload: <1s** ✅ unchanged
- **Code reload: ~5–6s** (was: 2s)

Frame the code path realistically: "5-second iteration for code; sub-second for assets and scenes." This is still **faster than Unity** (~10-20s typical Domain Reload + Play), comparable to **Bevy** (~3-8s incremental), and slower than **GDScript** (~instant — but at the cost of Go's tooling story).

Update marketing accordingly. The honest pitch: "Go's tooling on Godot, with sub-second hot-reload for art/scenes and 5-second code iteration."

### Option B: Pursue link-time optimization upstream

The 5.7s is dominated by linking ~hundreds of small Graphics.GD packages. Options that might claw back time:

- **`go build -gcflags='-l' -ldflags='-w -s'`** — disable inlining (already does this for classdb only in `gd build` per main.go:248). Worth measuring.
- **Smaller Graphics.GD subset** — if a gogogd user could opt into "only the Godot classes I use," the link cost drops. Requires gogogd-side codegen to tree-shake the imports. Plausible Phase 2 work; speculative.
- **PIE binary mode** — sometimes faster than c-shared but Godot's GDExtension protocol requires c-shared. Not viable.
- **`-buildmode=plugin`** instead of `c-shared` — Linux/macOS only; non-portable.

These are weeks of work for a small reduction. Defer until Phase 1 ships with the honest budget; if iteration friction becomes the #1 complaint, invest then.

### Option C: State-preserving reload (Phase 4+ already)

The killer feature is *not* fast Go builds — it's that the user doesn't lose their seat. State-preserving reload (Phase 4+ per the plan) would mean: rebuild in background, hot-swap classes, keep the game running. Even if that takes 5s in the background, the user doesn't notice because they're still playing. This is the bigger leverage point.

Already in the plan; this POC reaffirms it's the right long-term bet.

### Option D: Accept and ship

5-6s code iteration is slower than ideal but **still well above the "flow-breaking" threshold** (~10s). Jam developers and prototypers will tolerate it. The current Bevy / gdext / Unity-with-domain-reload ecosystems live with similar numbers. We're not worse than the competition — we'd just be over-claiming with the 2s target.

## How to reproduce

```pwsh
$env:CC = 'C:\Users\hello\gd\bin\zig.exe cc'
$env:CGO_ENABLED = '1'
Set-Location C:\Projects\gogogodot\poc\01-register-lifecycle

# Incremental build measurement
Measure-Command {
    # ...edit a line in main.go to invalidate the cache...
    go build -buildmode=c-shared -o graphics\windows_amd64.dll .
}

# Full run measurement
Measure-Command {
    Set-Location graphics
    C:\Users\hello\gd\bin\godot.exe --headless
}
```

Numbers will vary per machine. The dominant signal is the **5+ second link step** — if your build is significantly faster or slower, it points to your toolchain config rather than your code.
