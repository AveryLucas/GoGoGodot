# POC #8 — Wrapper-Type Method Forwarding

**Status:** PASS — retires R3
**Date:** 2026-05-21
**Graphics.GD version:** `v0.0.0-20260521203745-bcb92de10087`
**Godot version:** `4.6.2.stable.official.71f334935`
**Risk addressed:** R3 — "embedding `Node2D.Extension[T]` through an extra wrapper layer trips Graphics.GD's class registration."

## Hypothesis

ARCHITECTURE.md §6 strategy: hand-write a `gogogd.Node2DExt[T]` shim that embeds `Node2D.Extension[T]` and adds method-forwarding so users write `p.SetPosition(v)` instead of `p.AsNode2D().SetPosition(v)`.

`register_class.go:146` does a `trivialExtension` check — `classType.NumField() == 1 && Field(0).Type == underlyingType`. Our wrapped Player struct has an extra wrapper layer AND additional fields, so it's not trivial. The fallback check (`classType.ConvertibleTo(underlyingType)`) may or may not succeed depending on Go's generic-aware conversion rules. If neither succeeds, a soft warning fires (line 148 has a FIXME to make this a hard error eventually).

The question: does this pattern work today? Does it warn? Does it break anything observable in Godot's class hierarchy?

## Test setup

```go
type Node2DExt[T classdb.Class] struct {
    Node2D.Extension[T]
}

func (e *Node2DExt[T]) SetPosition(v Vector2.XY) { e.AsNode2D().SetPosition(v) }
func (e *Node2DExt[T]) Position() Vector2.XY    { return e.AsNode2D().Position() }
func (e *Node2DExt[T]) SetName(name string)     { e.AsNode().SetName(name) }
func (e *Node2DExt[T]) Free()                   { e.AsNode().QueueFree() }

type Player struct {
    Node2DExt[Player] `gd:"Player"`

    HP     int            // exported field
    Helper Node.Instance  // child wiring test
}

func (p *Player) TakeDamage(n int) int { ... }  // GDScript-callable
func (p *Player) Ready() { ... }
func (p *Player) Process(delta float32) { ... }
```

Then a GDScript Inspector node introspects `Player`'s class hierarchy, methods, and properties.

## Findings

### 1. ✅ The wrapper-type strategy works exactly as §6 imagines

Eight separate checks all green:

| Check | Result | Why it matters |
|---|---|---|
| `classdb.Register[Player]()` succeeds silently | ✅ no warning | "trivialExtension" check doesn't fire for this layout |
| Godot sees the class as `Player` | ✅ `get_class() == "Player"` | The wrapper isn't itself registered |
| Inheritance chain preserved | ✅ `is Node2D`, `is Node` true; `is Sprite2D` false | Godot routes calls through the right parent class |
| `Ready` and `Process` fire | ✅ both confirmed | Lifecycle dispatch survives the extra layer |
| `gd:"path"` child wiring works | ✅ `Helper.populated == true` | The wiring reflection walk handles the wrapper |
| Forwarded methods work | ✅ `SetPosition((100,200)) → Position()=(100,200)` | The whole point of the shim |
| User methods exposed to GDScript | ✅ `take_damage(7) → 43` | Method registration sees through the wrapper |
| Exported fields exposed | ✅ `player.hp == 43` after `take_damage(7)` | Property registration sees through the wrapper |

### 2. The `trivialExtension` warning is a non-issue (for now)

Line 148 of `register_class.go` says: "FIXME enable this as a strict safety check at some point." Today it's a soft warning, and **it didn't fire for our wrapped class layout**. Why not? My best read of the condition (`!trivial && classType != underlyingType && !classType.ConvertibleTo(underlyingType)`): Go's structural conversion rules likely consider `Player` convertible to its underlying type because the wrapper's first-field embedding is structurally compatible.

**Forward risk:** if upstream enables this as a strict check, the wrapper pattern breaks. Mitigations, in order of preference:

- Pin Graphics.GD to a tested version in gogogd's go.mod, run a CI build on each upstream release to catch a regression.
- If/when upstream tightens the rule, switch the pattern to either (a) lobby upstream to officially bless the wrapper layout, or (b) generate the wrapper layer into the user's class via `go generate` instead of via embedding.
- Worst case fallback: gogogd ships `As*()`-style call sites everywhere and loses the §6 ergonomics. Acceptable but a step back.

Phase 1 should include a CI test that registers a wrapped class and asserts no warning is logged — early-warning system for upstream changes.

### 3. ⚠️ Forwarded methods leak into Godot's method DB

`has_method("set_position") = true` from GDScript. That's true regardless of our wrapper (Node2D has a built-in `set_position`), so this isn't proof of leakage by itself. But there's a more subtle concern: our wrapper's `Free()` and `SetName()` ARE exported Go methods on `*Node2DExt[T]` and so will be considered for GDScript registration when `Player` (which embeds `*Node2DExt[T]`) is registered.

Looking at `register_methods.go:36-44`:

```go
_, inherits := rtype.FieldByName("ExtensionInherits")
parent, ok := rtype.FieldByName("Class")
if !ok && !inherits {
    panic(...)
} else if ok {
    if _, ok := reflect.PointerTo(parent.Type).MethodByName(method.Name); ok {
        continue  // skip — already defined on parent
    }
}
```

The skip path covers methods *inherited from the upstream Class field*, not methods inherited from the **wrapper** layer. So `Free` and `SetName` might be exposed to GDScript as `free` and `set_name`. From the inspector output: `has_method('set_position') = true` is ambiguous (it's a built-in). Worth a follow-up test, but **not blocking**. Worst case, gogogd registers wrapper methods under names that already exist; Godot's resolver handles collision gracefully or warns. Phase 1's `gogogd inspect <type>` should list all exposed methods so we can audit.

### 4. ✅ Inheritance chain preserves correctly

`player is Node2D == true` is the proof. If the wrapper had broken Godot's class-graph view, `is Node2D` would be false. Phase 1's wrapper-type inheritance ladder (`NodeExt → Node2DExt → CharacterBody2DExt → ...`) can be assumed safe.

### 5. The `gd:` tag on the user struct controls Godot's registered name

`gd:"Player"` on the embedded `Node2DExt[Player]` field controls what Godot sees. Without it, the registered name would be `Player` anyway (defaults to the struct name), but the tag is the explicit lever — useful when codegen-generated wrappers might otherwise get awkward names. Confirmed working through the wrapper layer.

## What this means for the plan

| Plan item | Action |
|---|---|
| Phase 1B wrapper types | **Greenlit.** The 30 hand-written `*Ext[T]` types in the package layout can be implemented as planned |
| Wrapper inheritance ladder | Build bottom-up: `NodeExt → CanvasItemExt → Node2DExt → CollisionObject2DExt → ...`. Each shim layer adds its own forwarders; transitive method promotion via embedding |
| `gogogd doctor` | Add a self-test that registers a known wrapped class and asserts zero warnings from `classdb.Register`. Catches upstream regression early |
| Phase 4 codegen wrappers | Same pattern proven safe — codegen can generate `*Ext[T]` types for the full Godot class surface |
| `gogogd inspect <type>` (Phase 2) | Should list method names actually exposed to GDScript, since the wrapper layer may surface unexpected forwarders (item 3 above) |
| ARCHITECTURE.md §6 | Currently says the pattern is "the central API decision." Now empirically validated — keep, with a callout that `register_class.go:148`'s FIXME is the only thing that could break it, and the CI lint protects against upstream regression |
